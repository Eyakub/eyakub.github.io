Off this path: A stampede is many misses at once. One caller restocks while the others wait, or the timers differ. Do not let every miss hit the database.

The app does cache-aside. A plain GET is constant time. One thread runs commands, so a long command makes every other client wait. I/O threads can move socket work off that thread.

A miss returns nil. The app, not Redis, decides to load the database. Redis does not stay in sync with it.

The database is the source of truth. Cache-aside means the app owns the miss, the load, and the later copy. Read-through would hide that inside the cache.

SET with EX stores the copy and a TTL in seconds. On a later write, delete the key. A timer alone can still leave a stale copy until it ends.

A hit skips the database. INFO stats counts keyspace hits and misses. The Celery page is the job queue, not this cache.

No maxmemory is the 64-bit default, so nothing is evicted. The default noeviction then rejects writes that need memory. Prefer allkeys-lru for a cache. TTL-only policies refuse writes when no key has a TTL. LRU and LFU sample keys.

Snapshots to dump.rdb are on by default and can lose minutes. The log stays off until appendonly yes, and its default fsync can drop about one second. Use both for stronger safety. Since 7.0 the log is a base file, increments, and a manifest.

Pub/sub is at-most-once. An offline subscriber misses the message, and there is no ack. Streams keep history, ids, and consumer groups when you need a replay.
