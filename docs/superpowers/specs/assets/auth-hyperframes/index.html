Off this path: An intercepted authorization code without the code_verifier returns invalid_grant. Public clients must send PKCE. For confidential clients it is recommended.

A code_verifier is 43 to 128 unreserved characters, fresh for each request. The client sends code_challenge, the base64url SHA-256 of that secret, with method S256. Use plain only if the client cannot do S256.

The browser is sent to the authorization endpoint with response_type=code, the client id, the code_challenge, and a state value. redirect_uri must match a registered address by exact string comparison. state comes back unchanged so the client can reject a forged return.

The resource owner authenticates only with the authorization server, so the password never reaches the client. The server then asks what the client may do. Public clients must use this code flow with PKCE. The password grant is not allowed.

The authorization server redirects back with a one-time authorization code and the same state. The code must expire shortly. Ten minutes is the recommended maximum. Using a code twice must be denied, and tokens already issued from it should be revoked.

The token request is a back-channel POST with the code and the code_verifier. The server hashes the verifier and compares it to the stored challenge. A mismatch returns invalid_grant. The secret never traveled through the browser.

The server returns an access token and, optionally, a refresh token that is sent only back to the authorization server. The spec fixes no lifetime. expires_in is recommended when one is set. OpenID Connect (OIDC) may add an id_token.

The client calls the API with Authorization: Bearer and the access token, a JWT. The API checks the signature and exp locally, and refuses when aud is present and does not name this API. No call back to the authorization server.
