Off this path: PostgreSQL aborts one transaction in a lock cycle. Which one is not predictable, so the aborted transaction must be retried. Lock rows in the same order.

The planner reads the question and the table statistics, then picks a sequential scan or an index scan. EXPLAIN shows the plan and its cost. It does not run the query.

With no usable index the plan is a sequential scan. It reads every row, so the cost grows with the whole table, not with the number of matches.

A B-tree is the default index. It serves equality and range checks, then the row is read from the table. On columns a, b the index is most useful when the query constrains a. A query on only b usually will not limit the scan.

BEGIN groups the writes. The log of those writes is flushed before the data pages must be, and that flush is what makes COMMIT durable by default. ROLLBACK drops the group. synchronous_commit off reports success before the flush.

Read Committed is the default. Each statement sees only rows committed before that statement, and Read Uncommitted does the same, so dirty reads do not happen. Repeatable Read uses one snapshot for the whole transaction.

Lazy loading runs one query for the parent rows and another query per child. selectinload gathers those children with one IN query. joinedload uses one join, and a collection then needs unique(). Async sessions cannot do the lazy load, because implicit IO is not allowed.

The rows come back. A pool reuses connections instead of opening one per question. Ask for a page of rows, not the whole table. ANALYZE refreshes the statistics the planner used on the first step.
