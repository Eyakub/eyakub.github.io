return mapping[key]

Off this path: A worker that waits on a future from the same pool can deadlock, including when max_workers is 1. if key in mapping then mapping[key] can miss, because another thread can delete the key between the check and the read.

Threads in one process share the heap. That is the point and the hazard. Separate processes do not share it.

A race condition is an outcome that changes with timing. x += 1 is several bytecode instructions and is not atomic. The GIL does not make that update safe.

The glossary data race is several threads, the same memory, at least one write, and no synchronisation. It happens in native code, which a Python API may expose. A pure-Python timing bug is still a race condition. The names are not synonyms.

A Lock is not owned, so any thread may release it. An RLock is owned by the thread that took it, and that same thread may take it again. Two locks in opposite order is the deadlock on the locks page.

The lock orders this update before the next thread's read. Without it, the other thread can see a half-changed object. On a free-threaded build, dict and list use per-object locks, and a lock-free read can still see an in-between state.

Since 3.13, ThreadPoolExecutor defaults to min(32, (os.process_cpu_count() or 1) + 4). It reuses idle workers. The pool joins them before the interpreter exits, so do not park a long task there. queue.Queue is the safe handoff if you build the workers yourself.
