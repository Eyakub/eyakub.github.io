Off this path: Python does not detect a deadlock. A global order, always Lock A then Lock B, removes the circular wait. threading.Lock is not reentrant; a second acquire in the same thread hangs. Use RLock when one thread must take the lock again.

counter += 1 is load, add, store, not one step. Thread 1 loads 0 into its own private stack.

A thread switch between the load and the store is allowed at bytecode boundaries, even with the GIL.

The add happens on Thread 1's private value. The shared counter is untouched.

The store completes. Thread 2 does not know the counter has changed.

Lost update from a non-atomic read-modify-write. On modern CPython it often needs many iterations to show, but it is a real bug.

with lock: calls acquire() and guarantees release() in a finally, even if an exception is raised.

Lock.acquire() blocks until the lock is released. It also accepts timeout= or blocking=False.

This is the critical section. No other thread that needs the same lock can interleave with it.

Leaving the with block releases the lock. Thread 2's blocked acquire() then returns.

Serialised increments give the right result, but waiting costs throughput. Prefer designs that avoid shared state, such as queues.
