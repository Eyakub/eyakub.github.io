@app.task(bind=True, autoretry_for=(TimeoutError,), acks_late=True)

generate_report.delay(user_id=42) · AsyncResult(task_id).state

Off this path: A TimeoutError with autoretry_for becomes RETRY, then FAILURE after max_retries. A countdown past visibility_timeout can deliver the task twice, so the task must be idempotent.

An HTTP POST reaches a FastAPI route. Building the PDF takes about 30 seconds, far too long to keep this request open.

generate_report.delay(user_id=42) serializes the task name and arguments to JSON and pushes the message onto the celery list in Redis, the broker.

The route returns 202 Accepted with the task id. Response time stays in milliseconds no matter how slow the job is.

The worker fetches with BRPOP and reserves up to 4 messages per process ahead of time (worker_prefetch_multiplier). Redis has no real acks, so Celery keeps an unacked copy and hands it out again after visibility_timeout, 1 hour by default.

The task runs in a prefork child process, one per CPU core by default. The message is acknowledged just before the task starts. acks_late=True moves that to after it finishes.

State and return value are written to the result backend under celery-task-meta-<id>. They expire after result_expires, 1 day by default.

The client polls a status endpoint. WebSockets or server-sent events can push the update instead.

AsyncResult(task_id).state reads the backend. An unknown or expired id also comes back as PENDING, so PENDING does not prove the task exists. Never call .get() here. It blocks.

The backend returns state SUCCESS and the task’s return value, deserialized from JSON.

The status endpoint returns 200 with the result. The API spent only milliseconds on this user the whole time.
