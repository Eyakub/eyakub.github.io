Off this path: A scheduler can keep picking the same task, so a ready task starves. An asyncio task that never awaits never returns to the loop. await asyncio.sleep(0) is enough to suspend.

One core takes task A from the ready queue and runs it. Other ready tasks are in progress, not running. Only one task executes on a core at a given instant.

A blocking call parks A. The core is released instead of spinning, which is the gap interleaving uses. Waiting on a disk, a socket, or a lock all look like this.

The core runs B during A's wait. Two tasks are in progress and only one executes. That is concurrency. Parallelism would be both executing at the same instant, which needs another core.

The wait ends and the scheduler puts A back on the ready queue. A does not seize the core. Something still has to pick A.

A context switch saves B's program counter, registers, and stack pointer, then can restore another task. That save is why tiny slices can cost more than they save.

A is restored and runs again. B is ready, not gone. One core made progress on two tasks by interleaving. It never ran both at once.

Cooperative tasks run until an await that suspends. Preemptive: the OS interrupts a thread. A GIL build asks to switch between bytecodes. setswitchinterval sets the ideal slice, 5000 µs in CPython 3.14, often longer. The OS, not Python, picks who runs next.
