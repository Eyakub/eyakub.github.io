Off this path: A free-threaded build can run bytecode on two cores. Compound updates can still race, and an unsafe C extension can turn the GIL back on.

A thread must hold the GIL to run Python bytecode. Only one thread can hold it at a time.

The eval loop executes T1's bytecode. The GIL protects interpreter internals such as reference counts and built-in containers.

T2 is runnable but blocks on the GIL's condition variable. It cannot execute any Python code until it gets the GIL.

After the switch interval (default 5 ms) a waiter sets a drop request. The holder yields at its next check between bytecodes, so the timing is advisory.

The holder releases the GIL. With a forced switch, another waiter must take it, so the releaser cannot instantly grab it again.

Which waiting thread wins is the operating system's decision. The interpreter has no scheduler of its own.

Blocking I/O calls release the GIL before they wait. T2 sits in the kernel while T1 runs Python code: a real overlap of waiting and computing.

When the I/O call returns, T2 must re-acquire the GIL before it touches any Python object.

Some C extensions, such as hashlib on big data, zlib and NumPy, release the GIL around heavy work. Many extensions do not.

The C call and T2's bytecode run truly in parallel, on two cores.

Returning to Python code means re-taking the GIL. The GIL limits parallel Python bytecode, not every kind of parallel work.
