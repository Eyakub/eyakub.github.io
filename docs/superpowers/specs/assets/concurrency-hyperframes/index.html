Off this path: On a GIL build, CPU-bound threads take turns, so both finish near 2t, not t. Use processes for that work.

One core takes task A from the run queue and executes it. At any single instant a core runs only one thing.

Task A blocks on slow I/O. The core is released instead of spinning, and that is what makes interleaving possible.

The core runs B during A’s wait. Two tasks are in progress but only one executes at a time: that is concurrency.

A’s I/O completes, so A can resume. The switch is a context switch for OS threads, or a resume at await in asyncio.

A completes and B continues on the same core. Total time beats running A then B, because B used A’s idle time.

One core progressed two tasks by interleaving. Concurrency does not need more than one core.

Two cores execute two instruction streams at the same instant: parallelism. It needs more than one core and a runtime that can use them.

Two equal CPU-bound jobs take about half the wall-clock time, minus overhead. Interleaving alone only helps when tasks wait.

Concurrency is how work is structured and scheduled. Parallelism is simultaneous execution, which needs several execution units.
